Projects organize work that takes multiple [issues](/issues) to finish — a product launch, a migration, or a feature delivered in stages.

Work that a single issue can describe does not need a project. Projects fit a group of work that shares a goal, needs its progress tracked together, or needs shared repositories and working directories.

## Parts of a project

| Part | Purpose |
|---|---|
| **Name, icon, and description** | Goal, scope, and long-lived requirements; the description enters the execution context of agents working inside the project. |
| **Status** | `planned`, `in_progress`, `paused`, `completed`, or `cancelled`. |
| **Priority** | `urgent`, `high`, `medium`, `low`, or `none`. |
| **Lead** | A member or an agent — who coordinates the project. |
| **Start and target dates** | The project's planned time range. |
| **Issues and progress** | The work in the project and how much of it is finished. |
| **Resources** | Linked GitHub repositories or local directories on specific computers. |
| **Workflow** | The steps its issues follow and who takes over at each step. |

## Browse projects

Open **All projects** and use the display menu to choose **Table** or **Board**. Both layouts support search and filters for status, priority, and lead. Group by status, priority, lead, or [folder](#folders); the table can also stay ungrouped. On the board, dragging a project to another column changes that field.

The table can show start date, due date, progress, and last activity. Sort by those fields, name, status, priority, or creation time. Layout, grouping, sorting, visible columns, and filters are saved per user and workspace across devices; search text is not saved.

## Projects and issues

A project can contain any number of issues; an issue belongs to at most one project. Create issues directly inside the project, or pick or change the project from the issue's properties.

Project progress is computed automatically from linked issues:

```text
progress = issues whose status is in the done or closed category ÷ all issues in the project
```

Among the built-in statuses that means `done` and `cancelled`; custom statuses in those two categories count as well. `cancelled` means that work has been closed out of the project's scope, so it counts toward progress.

Project status and issue status are independent: finishing every issue does not set the project to `completed`, and changing the project's status does not bulk-change its issues.

## Project description and execution context

When an agent runs an issue inside a project, the project's name and description are added to that run's context. Put what every related run needs to know in the description — the goal, technical boundaries, delivery conventions — and keep requirements for a single issue in that issue.

## Add resources

Project resources tell agents which code and working directories to use:

- **GitHub repositories**: provide a repo the runtime can check out, with an optional ref.
- **Local directories**: let the runtime on a specific computer use an existing directory; the agent either edits it directly or works in an isolated git worktree of it.

See [Project resources](/project-resources) for how to choose and for the safety boundaries.

## Choose a workflow

Choose the project’s **Workflow** to set its board columns and who takes over at each step. For example, development can go to one agent, review to another, and acceptance to a team member. Projects without another choice use **Default**: every status is available and nothing is handed off automatically. See [Workflows](/workflows) for setup and switching an existing project.

## Project lead

The lead can be a member or an agent; a member who is the lead can also switch the project’s workflow. Making someone the lead does not assign issues to them or start any work. To hand a step to the lead, set that step's handler to **Project lead** in the workflow.

## Folders

Folders group related projects, such as everything for one launch or one team, so the sidebar's Projects section stays short. Owners, admins, and members share the same folders and can create, rename, or delete one and move projects in and out of it. A project is in at most one folder, and folders do not nest. A folder only organizes projects; it does not change who can see them.

- **Create a folder**: click **+** on the sidebar's Projects section and choose **New folder**, or choose **Move to folder → New folder…** in a project's menu to create one with that project in it.
- **Move a project**: choose **Move to folder** in the project's menu, or drag the project onto a folder in the sidebar, or out of it. When creating a project, pick its folder in the create dialog; **+** on a folder row creates a project in that folder.
- **Rename or delete a folder**: right-click it in the sidebar. Deleting a folder moves its projects back to the top level; nothing else changes.

Which folders are open in your sidebar, and the order of folders and projects, are personal and do not affect other members. The Projects section's filters apply inside folders: a folder whose projects are all filtered out is hidden, while an empty folder stays visible so you can fill it. On **All projects**, group by **Folder** to see each folder's projects together; on the board, dragging a project to another column moves it to that folder.

## Pin to the sidebar

A pinned project appears in your sidebar. Pinning is a personal preference and does not affect other members.

In the Projects section settings, **Default icons only** replaces custom project icons with the default project icon in that section. It is off by default and does not change the projects themselves.

## Archive and restore

Choose **Archive project** in the project's menu, or **Archive** from the project list. Anyone who can edit the project can archive or restore it. Archiving hides it from ordinary project lists and pickers and prevents new issues from being created in or moved into it. Existing issues, history, and settings remain; existing issues can still be read and edited. The project's status does not change.

Active autopilots that create issues in the project are paused. To restore the project, switch the project list's title menu to **Archived projects** and choose **Restore**, or use **Restore project** on its page. Restoring does not resume those autopilots; enable them separately when ready.

## Create, edit, and delete

Owners, admins, and members can create and edit projects. Members can delete projects they created or that an agent they currently own created; agents can delete only their own projects. Human `owner` and `admin` members can delete any project, including older projects with an unknown creator.

<Callout type="warning">
Deleting a project does not delete its issues: they detach and stay in the workspace. The project's description, status, and resources are permanently deleted.
</Callout>
